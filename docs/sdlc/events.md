# Events

Scrum events create regularity and minimize non-essential meetings. In Field Techy, they structure sprints for application development.

## Sprint Planning

| Aspect | Details |
|--------|---------|
| **Duration** | 2 hours for a 2-week sprint. |
| **Participants** | Entire Scrum Team. |
| **Purpose** | Define sprint goal and select backlog items. Set start and end dates for selected items. |
| **Activities** | PO explains each user story; assignee is assigned; story points are negotiated with the assignee or team; dates set based on negotiation. |
| **Output** | Sprint Backlog and goal (e.g., "Deliver client job posting feature"). |

## Daily Scrum

| Aspect | Details |
|--------|---------|
| **Duration** | 15 minutes, daily. Any additional discussion should be conducted under individual meetings |
| **Participants** | Development Team (PO and SM optional). |
| **Purpose** | Synchronize progress and plan the next 24 hours. |
| **Format** | Each member answers: What did I do? What will I do? Any impediments? |
| **Blocker Communication** | Any issues/blockers must be communicated immediately. See [Team Communication](communication.md) for templates. Also communicate formally via the WhatsApp group and inform team members during the next sprint meeting, keeping it brief since details are available in the posted message. |
| **Benefits** | Identifies blockers early, like API integration issues in Field Techy. |

## Sprint Review

| Aspect | Details |
|--------|---------|
| **Duration** | 1 hour. |
| **Participants** | Scrum Team and stakeholders. |
| **Purpose** | Inspect the Increment and adapt the Product Backlog. |
| **Activities** | Team demos work; PO discusses backlog changes. |
| **Outcome** | Feedback for improvements, e.g., UI refinements for engineer portals. |

## Sprint Retrospective

| Aspect | Details |
|--------|---------|
| **Duration** | 30 minutes. |
| **Participants** | Scrum Team. |
| **Purpose** | Reflect on the sprint and plan improvements. |
| **Activities** | Each team member explains using the KPT framework: Keep (what went well to continue), Problem (issues faced), Try (actions or experiments for improvement). Identify non-performing team members for coaching. Discuss actions (e.g., improve testing processes). Plan code freezes before sprint ends for stability if needed. |
| **Focus** | Continuous improvement, such as adopting better code review practices. |

## General Guidelines
- All events are time-boxed to maintain focus.
- No changes to Sprint Backlog during the sprint except by the Team.
- In Field Techy, events ensure alignment on features like authentication or notifications.

These events promote transparency, inspection, and adaptation.
